# 学术表达与 academic-humanizer 协作

目标是让论文按照已确认学科、层次和研究路径清楚、自然、可信地展开论述。采用作者既有的人称和术语；“本系统”仅用于系统实现类内容，不强制其他论文套用工程语气或英文论文的 we。若有作者样文，参考其句式与叙述节奏；样稿事实不可移植。

## 执行方式

新写章节先完成事实与方法审查（软件路径为技术审查），再进入表达审查。已有段落仅润色时，复用有效审查结论，核对本轮涉及的事实、数字和引用；没有事实变更不从头取证全项目。若能找到 `academic-humanizer`，读取并遵循其审查、改写和简短变更记录流程；不复制或修改该技能。将当前正文、已有定位、必要证据映射和本指南一同用于本轮改写。此处“协作”指按阶段应用规则，不要求创建其他聊天或代理。

不可用时按本指南独立审查，交付时说明采用了内置表达规则。基础流程保持可用，无需让用户先安装第二个技能。

先记录问题和改法，再修改本轮任务范围内确实需要的句段。保护原始数字、结果、公式、技术符号、引用及必要限定；润色发现事实问题交回技术审查，有证据后单独更正，不能偷偷改数。正常润色保留段落职责和信息覆盖；结构重组仅在用户已授权的范围内进行，已有授权无需重复确认。

## 去掉机械防御，保留有意义的限制

对下列写法的修改必须满足所述事实已在 Evidence 中核实；例句是表达示例，不是待套入项目的事实。

| 常见问题 | 核实后的正文表达 |
| --- | --- |
| “从当前仓库可以看出，系统似乎使用了 JWT，但不能作为最终判断” | “系统采用 JWT 传递登录身份，服务端在请求处理前校验令牌。” |
| “这个数据库结构是我们自己设计的，只能说明项目里有相关内容” | “数据库围绕核心业务实体设置数据表，并通过关联字段组织业务数据。”具体关系仍须展开 |
| “这里只能说明存在权限判断，不能证明安全性” | “服务端校验操作人的角色及资源归属，拒绝不满足条件的请求。”若只校验角色，不增加资源归属 |
| “系统高并发性能优秀” | 用真实测试条件与结果替换；没有实测就删除效果结论，不补造数据 |

已确认实现直接用“采用、设置、校验、保存、返回”等准确动词。源文件名、核查过程和证据等级通常放 Evidence 或审查记录，正文只保留解释关键机制所需的定位。

保留会影响判断的范围：“本地环境”“本组用例”“该批次测试”“尚未进行外部服务联调”。这类信息集中安排在测试方法、结果解释或局限段落，但不能从具体性能结果旁删除适用条件。证据仅支持可能性时，保留“可能”“提示”等合适措辞；关键事实未知就标待确认，不靠“似乎”掩盖。

## 句段审查

- 每段推进一个论点，用具体业务约束、处理关系或结果支撑，衔接围绕数据和业务变化展开。
- 删除“随着……飞速发展”“具有重大意义”“极大提升”等无依据套话，以及重复的“首先、其次、最后”。
- 技术名词用同一称呼；不要为避免重复乱换术语。长句按处理步骤或因果关系拆分。
- 说清问题、选择、机制及结果，不把所有段落硬套同一模板，也不把核心流程压缩成一句功能介绍。
- 核心论述压缩或深度不足时，按 [章节深度指南](chapter-quality.md) 引用原稿位置，分别检查事实与关系解释；删重复后主体、条件、状态和失败出口仍完整。已有局部改写按其范围复核，不强制全文打分。
- 不添加主观感受、虚构开发经历、口语、营销话术或夸大的创新与效果。
- 不承诺规避 AI 检测、查重或学校披露要求。评价表达质量依据准确性、清晰度、连贯性和作者语气。

改写后核对本轮涉及的技术事实、所有数字与引用、段落覆盖、图表及上下文。已有审查记录时就地更新；跨章节或跨会话任务将简短变更记录保存在 review/，简单段落修改可在回复中说明，不强制新建目录。记录不要夹入正文。
