# 原项目规范的通用段落摘录

本对照只采用下列原文通用段落，排除原项目专属模块、技术栈、学校格式和字数目标。不是原项目全套规则效果对照。

## 2. 交付物验收门槛

| 阶段 | 必须交付 | 通过条件 |
|---|---|---|
| Scope / 基线 | 论文目录、任务边界、当前工作区快照（可记录 HEAD 和未提交变更）、已有稿件和待核实事项 | 能说明本轮针对哪个代码状态和哪些章节；当前工作区包括未提交修改也可作为有效基线，不要求先提交或冻结 |
| Evidence | 模块或章节事实表、证据来源与确认等级 | 每项关键事实指向文件/类/方法/表/配置/测试记录；区分代码实现、脚本定义、配置声明、运行观察和测试结果 |
| Design | 章节蓝图及“论点—证据—正文位置”映射 | 每个既定标题有写作任务、证据、论证次序和缺口；图表有明确用途；相邻章节重复已标出 |
| Draft | 所有约定章节的完整正文 | 不是提纲、摘要或示范段；核心业务讲清角色、触发条件、处理链、数据/状态变化和适用的异常边界 |
| Technical Review | 按源代码和数据结构复核后的修订稿、技术审查记录 | 关键结论逐项有证据；角色、权限、字段、状态、事务、异常及已实现/未实现边界无冲突 |
| Academic Review | 完成逻辑、章节衔接、术语、重复、语言和论述充分性检查的正文 | 保留技术论证所需细节；删去重复和空话，不以“精简”为由把流程压成一句功能介绍 |
| Final | 合并稿、未决事项清单、字数/目录/图表/引用核对记录 | 各章与分章稿一致；待确认内容显式保留；Word 版按学院规范渲染检查后再称为格式定稿 |

## 3. “描述完整”的判定方式

篇幅是警报，不是质量本身。正文的每个核心主题都要回答与该主题有关的问题，不能只写功能名称或采用了什么技术。

### 3.1 核心业务论证链

对职位投递、企业审核、简历、面试、聊天、匹配等核心业务，按证据说明：

1. **业务主体和触发：**谁从哪个页面、接口或消息入口发起，解决什么具体任务。
2. **前置条件和规则：**身份、资源归属、状态、必填数据、重复操作或名额等条件。
3. **处理过程：**前端请求如何经过 Controller、Service 及必要组件；关键分支如何选择。
4. **数据变化：**读写哪些核心表/字段，是否涉及 Redis、外部服务或实时推送；状态如何变化。
5. **结果、失败与边界：**用户获得什么结果，哪些错误会被拒绝、回退或留待确认；当前实现有什么限制。
6. **依据和章节作用：**证据来自哪里；本节补充的是需求、设计、实现还是测试结论，避免重复上一章。

并非每节都要硬套六项。绪论、技术原理和结论按各自任务写；不存在或证据不足的环节明确说明，不补造流程。

### 3.2 段落质量

- 每段有一个主要论点，并用事实、处理关系或对比支撑。连续段落应形成“问题—方案—机制—结果/限制”的推进关系。
- 模块实现不能只写“系统实现了 X”。至少展开入口/调用链，以及数据、规则或失败边界中的关键部分；重要模块还要说明设计选择与业务约束的关系。
- 表格用于集中比较角色、数据表、需求、测试结果等信息；表后解释影响业务理解的关系，不把表格当正文替代品。
- 图示须对应源代码的真实流程。图中有多个分支时，正文解释主要分支和状态，不能只贴图不解读。
- 源码符号用于定位关键机制；正文解释机制及作用，不逐行翻译代码，不复制大段代码。



## 项目真实性

每个关于功能、架构、数据库、接口、权限、消息、缓存、状态、测试、技术选型或性能的关键陈述，都必须能追溯到代码、SQL、配置、接口文档、Evidence 或用户明确提供的信息。无法核实时标注【待确认：……】。

取证时记录当前代码提交号和未提交文件，并区分“源码中存在”“配置声明”“指定环境中观察到”“测试执行通过”。Evidence 按模块维护，记录入口、关键类/方法、数据表、缓存/实时组件、权限、状态约束、异常路径和待确认项；正文只保留论证需要的实现细节，不把依赖声明或测试源码写成运行结果。

事实层级细分和章节验收条件见 `thesis/quality-standards.md`。对于需求来源、运行状态、测试结论、数据库脚本与运行库差异，必须使用准确的证据类型措辞。

## 技术描述

不要只列技术名称。说明该技术在本系统哪个环节发挥作用，以及它与业务流程、数据库或其他模块的关系。避免写成技术教程或源代码注释。

核心业务不能只用一两句概括。根据证据说明入口、处理链、重要校验、数据/状态变化及异常或已知限制；无需套用固定段数，但要让读者能够复述业务如何从发起走到结果。

## 设计理由与章节衔接

设计理由要落到具体业务约束、数据流或代码机制。相关技术原理在前文讲过后，后续实现章节应聚焦本系统如何使用，避免重复。

Academic Review 不以“越短越好”为目标。压缩重复内容时保留完整因果关系、关键字段/状态、权限判断和失败分支；不允许把已核实但较复杂的处理流程缩写成只剩功能名。

## 表达方式

优先写清业务问题、设计思路、处理流程、核心实现、数据处理以及异常与约束。可以使用真实类名、表名和字段名证明论述，但正文不应变成源码说明书。
